# 機能仕様書: コードブロック視覚検出

**Feature Branch**: `021-code-block-gray-detection`
**Created**: 2026-03-12
**Status**: Draft
**Input**: Issue#22 — 視覚的コード検出アプローチの検討

## ユーザーシナリオ & テスト *(必須)*

### ユーザーストーリー 1 - 灰色背景コードブロックの自動検出 (Priority: P1)

プログラミング技術書をOCR処理する際、灰色背景で表示されたコードブロックが自動的に CODE リージョンとして検出され、Markdown のコードフェンス（` ``` `）で囲まれた形式で出力される。

**優先度の理由**: 灰色背景のコードブロックは多くのプログラミング書籍で使われる最も一般的な表現形式。背景色分析のみで高精度に検出でき、既存パイプラインへの影響が最小。

**独立テスト**: 灰色背景を持つ TEXT リージョンの画像を入力し、CODE に再分類されることを確認するだけで検証可能。

**受入シナリオ**:

1. **Given** yomitoku が TEXT として検出した灰色背景のリージョン, **When** レイアウト検出処理を実行, **Then** そのリージョンが CODE に再分類される
2. **Given** 白背景の通常テキストリージョン, **When** レイアウト検出処理を実行, **Then** TEXT のまま変更されない
3. **Given** 灰色背景だがアスペクト比が極端に横長（帯状ヘッダー）のリージョン, **When** レイアウト検出処理を実行, **Then** TEXT のまま変更されない（コードブロックと誤判定しない）

---

### ユーザーストーリー 2 - FIGURE 誤検出コードの救済 (Priority: P1)

yomitoku がコードブロックを FIGURE として誤検出した場合でも、テキスト分析（記号比率 + 拡張キーワード）により CODE に再分類され、OCR テキストが出力される。現状 FIGURE はスキップされておりテキストが失われるため、これを救済する。

**優先度の理由**: 実画像検証で FIGURE の約80%がコードブロックの誤検出であると判明。FIGURE → CODE 再分類なしではコードテキストが完全に失われる。

**独立テスト**: コードブロックが FIGURE として検出されたページを入力し、CODE に再分類されてテキストが出力されることを確認。

**受入シナリオ**:

1. **Given** yomitoku が FIGURE として検出したコードブロック領域, **When** テキスト分析で記号比率が閾値を超える, **Then** CODE に再分類されOCRテキストが出力される
2. **Given** yomitoku が FIGURE として検出したフローチャートや図表, **When** テキスト分析で記号比率が閾値未満, **Then** FIGURE のまま維持される
3. **Given** FIGURE 内のテキストにプログラミングキーワードが2個以上含まれる, **When** 記号比率が閾値未満でも, **Then** キーワード条件で CODE に再分類される

---

### ユーザーストーリー 3 - TEXT リージョン内コードの検出 (Priority: P1)

yomitoku が TEXT として検出したリージョンの中に実際にはコードが含まれる場合、テキスト分析により CODE に再分類される。FIGURE のみの対応では全コードの39%しかカバーできないため、TEXT も対象とする。

**優先度の理由**: 実画像検証で全コードの61%が TEXT に吸収されていることが判明。TEXT + FIGURE 両方を対象にしないと実用的なカバー率にならない。

**独立テスト**: コードが TEXT として検出されたパラグラフを入力し、CODE に再分類されることを確認。

**受入シナリオ**:

1. **Given** `class Foo {` のようなコードが TEXT として検出されたパラグラフ, **When** テキスト分析を実行, **Then** CODE に再分類される
2. **Given** 日本語の通常本文テキスト, **When** テキスト分析を実行, **Then** TEXT のまま変更されない
3. **Given** yomitoku が `section_headings` と判定した TITLE リージョン, **When** レイアウト検出処理を実行, **Then** コード判定の対象外としてスキップされる

---

### ユーザーストーリー 4 - 断片化コードブロックの結合 (Priority: P2)

yomitoku が1つのコードブロックを複数パラグラフに分割した場合、bbox の垂直近接度に基づいて隣接する CODE パラグラフを1つの CODE リージョンに結合する。

**優先度の理由**: 分断されたコードブロックが個別の CODE リージョンとして出力されると可読性が低下する。ただし結合なしでも個々のコード断片はCODEとして出力されるため、基本機能は動作する。

**独立テスト**: 複数の隣接する CODE パラグラフを入力し、1つの CODE リージョンに結合されることを確認。

**受入シナリオ**:

1. **Given** 垂直ギャップが閾値以内の複数の CODE パラグラフ, **When** 結合処理を実行, **Then** 1つの CODE リージョンとして出力される
2. **Given** CODE パラグラフ間に日本語本文（non-CODE）パラグラフが挟まっている, **When** 結合処理を実行, **Then** 結合が打ち切られ別々の CODE リージョンとして出力される
3. **Given** `}` が `3` として OCR 誤読された短い断片, **When** 隣接する CODE パラグラフがある, **Then** 断片として識別され CODE ブロックに結合される

---

### ユーザーストーリー 5 - CODE リージョンの可視化と出力 (Priority: P2)

CODE リージョンがレイアウト可視化画像で視覚的に区別でき、標準出力に検出数が表示される。

**優先度の理由**: デバッグと閾値調整に必要だが、コア機能（検出・再分類）が先。

**独立テスト**: CODE リージョンを含む layout.json からレイアウト可視化画像を生成し、CODE が色分けされていることを確認。

**受入シナリオ**:

1. **Given** CODE リージョンを含む layout.json, **When** 可視化画像を生成, **Then** CODE リージョンが専用色で描画される
2. **Given** パイプライン実行, **When** コード検出が完了, **Then** 標準出力に `[CODE: N]` と検出数が表示される

---

### エッジケース

- yomitoku がコードと本文を1つの TEXT に結合した場合、灰色比率が希釈されて検出漏れになる可能性がある（threshold 未満）
- `}` が `3` として OCR 誤読されるパターンへの対応（断片結合で救済）
- 灰色帯ヘッダー（「リスト2.5 概念ごとに…」等）がアスペクト比フィルタで正しく除外されること
- コードを含まない書籍（SRE概念書等）で false positive が発生しないこと
- YAML ベースの IaC コード（CloudFormation 等）は記号比率・キーワードともに低いため検出困難

## 要件 *(必須)*

### 機能要件

- **FR-001**: システムは TEXT リージョンの画像を HSV 色空間で分析し、灰色画素の割合が閾値を超えた場合に CODE に再分類しなければならない
- **FR-002**: システムは灰色背景判定時にアスペクト比フィルタを適用し、横長の帯状リージョン（セクションヘッダー等）をコードブロックと誤判定してはならない
- **FR-003**: システムは FIGURE リージョンのテキストを分析し、記号比率（`{ } ( ) ; = < > [ ]` 等）が閾値を超えた場合に CODE に再分類しなければならない
- **FR-004**: システムは拡張キーワード（`class`, `def`, `func`, `import`, `return` 等、多言語対応）の出現数が閾値以上の場合にも CODE に再分類しなければならない
- **FR-005**: コード判定は記号比率とキーワード検出の OR 条件（いずれか一方を満たせば CODE）で動作しなければならない
- **FR-006**: システムは TEXT + FIGURE 両方のリージョンをコード判定の対象としなければならない（TITLE は除外）
- **FR-007**: 隣接する CODE パラグラフは bbox の垂直ギャップに基づいて1つの CODE リージョンに結合されなければならない
- **FR-008**: 短い断片（`}`、OCR誤読の `3`、1行コード等）は FRAG として識別され、隣接する CODE ブロックに結合されなければならない
- **FR-009**: CODE リージョンは Markdown コードフェンス（` ``` `）で囲まれた形式で出力されなければならない
- **FR-010**: CODE リージョンの検出結果は layout.json に記録されなければならない
- **FR-011**: 灰色背景検出の閾値、記号比率の閾値、キーワードリスト、結合ギャップ閾値は設定ファイルで外部設定化されなければならない
- **FR-012**: コード判定に使用する OCR テキストは yomitoku の既存テキスト出力を使用し、追加の OCR エンジン起動は不要であること

### 主要エンティティ

- **リージョン (Region)**: ページ内の矩形領域。タイプ（TEXT, TITLE, FIGURE, CODE）、bbox 座標、テキスト内容を持つ
- **コード判定結果 (CodeDetectionResult)**: 記号比率、キーワード出現数、灰色画素比率、最終判定（CODE/non-CODE）を含む
- **コードブロック (CodeBlock)**: 結合後の CODE リージョン。元の複数パラグラフの bbox を統合した外接矩形と結合テキストを持つ

## 成功基準 *(必須)*

### 測定可能な成果

- **SC-001**: プログラミング技術書のコードブロックの70%以上が CODE リージョンとして検出される（Recall ≥ 70%）
- **SC-002**: CODE と判定されたリージョンの80%以上が実際にコードブロックである（Precision ≥ 80%）
- **SC-003**: 25主要プログラミング言語のうち24言語以上のコードブロックが検出可能である
- **SC-004**: コードを含まない書籍（概念書等）で false positive が実用上問題にならない水準に抑えられる
- **SC-005**: コード検出処理がパイプライン全体の処理時間を有意に増加させない（追加処理時間 < 1秒/ページ）
- **SC-006**: 検出された CODE リージョンが Markdown コードフェンスで正しくフォーマットされ、既存の OCR パイプラインに統合される

## 前提・制約

### 前提

- yomitoku はレイアウトを TEXT / TITLE / FIGURE の3カテゴリのみで検出する（CODE カテゴリなし）
- コードブロックは yomitoku により TEXT または FIGURE として誤分類される
- FIGURE の約80%がコードブロックの誤検出（Java プログラミング書籍での検証結果）
- 全コードの61%が TEXT に吸収されている（同検証結果）
- yomitoku の OCR テキストは FIGURE 内のパラグラフ（`figure.paragraphs`）からも取得可能
- 記号比率 + 拡張キーワード併用で F1=90.2%（Java 書籍で検証済み）
- 閾値は1冊の書籍で最適化した値であり、他書籍で要チューニングの可能性がある

### 制約

- 白背景 + 等幅フォントのみのコードブロック（灰色背景なし）は灰色検出では検出不可（テキスト分析で対応）
- YAML ベースの IaC コード（CloudFormation）は記号・キーワードともに少なく検出困難
- `}` が `3` として OCR 誤読されるパターンは断片結合で対応するが、完全な救済は保証しない
- Guesslang は日本語書籍に不適（F1=15.6%）であり使用しない
- ファインチューニングは本 Issue のスコープ外

### 除外されたアプローチ

| アプローチ | 除外理由 |
|-----------|---------|
| Tesseract による判定 | yomitoku テキストで十分（2,000倍高速） |
| Guesslang | 日本語書籍に不適（F1=15.6%）、Python 3.9限定で環境非互換 |
| YOLO ファインチューニング | 学習データ収集・アノテーションの工数大 |
| 等幅フォント検出 | 実装が複雑で日本語混在での精度が不確実 |
